# Parquet 行组与页尺寸测量（2026-11-14）

## 结论与改动

本轮保留默认 **2,048 行/行组、512 行/页**，新增 [BenchmarkParquetLayout](../internal/export/parquet_layout_bench_test.go)，固定比较窄表和宽表的五种布局。没有调整生产默认值或扩展公共 API。

测量显示布局存在明确取舍：

- 保持 2,048 行组、将页增至 2,048 行，4/64 列原生写入耗时分别下降 12.7%/14.3%，文件减少 5.4%/6.4%。但无压缩选择性读取的 VFS 返回字节增加 31.5%，读取受管内存峰值约增至 3 倍。
- 8,192 行组 / 2,048 行页的宽表原生写入耗时下降 25.6%、文件减少 7.4%；writer 受管内存峰值增至 2.11 倍，所测 Snappy 过滤读取量增加 25.4%。
- 32,768 行组 / 2,048 行页的宽表写入收益低于 8,192 行组；writer 受管峰值为基线的 7.92 倍，进程 RSS 峰值中位数增加 10.4%，过滤读取量增加 43.5%。不适合作为本轮的通用默认值。

这些是受控合成输入的原生 writer/VFS 结果，不是 CSV/NDJSON 完整转换、DuckDB 对比或发布性能验收。测量时公共 `CopyOptions` 尚未暴露行组/页尺寸；内部 `ParquetWriteOptions` 已有显式配置，不从本轮数据直接推导统一配置。

后续已在 `CopyOptions` 增加 `ParquetRowGroupRows` / `ParquetPageRows`，详见 [公共 API](public-api.md#structured-export)。默认值仍为 2,048 / 512，调用方可按负载选择 8,192 / 2,048；增加了尺寸校验、分配前预算检查及布局任务身份。该接线变更未重新计时，下文性能数据对应原测量版本。

## 数据与方法

生产代码包含上一轮[数值批量编码](parquet-numeric-encoding-2026-11-13.md)；本轮没有修改生产 writer 或 reader。测量程序、二进制与相关源码 SHA256 均留存在证据目录。

Windows/amd64、Intel Core i7-10510U、Go 1.27.3、GOMAXPROCS=8，本地文件、默认 Snappy，未清除 OS 缓存。每种布局各预热 2 轮、正式 7 轮；每轮轮换布局顺序，隔轮反转，共保留 90 个样本，其中 70 个正式样本。场景串行运行，没有与测试、编译或独立校验并行。

每份数据为 100,000 行 × 4/64 列，按 BIGINT、DOUBLE、VARCHAR、BOOLEAN 循环排列；c00 为有序行号，其余各列 10% NULL。字符串混合高基数账号和低基数 Unicode/引号，浮点值为精确四分之一数值。输入按 2,048 行 DataChunk 生成后复用，排除构造成本。该生成器与此前六列/64 列文本转换 fixture 不同，不能跨报告比较绝对耗时或文件大小。

写入计时包含生产 `NewAtomicVFSByteSink`、writer 创建、批量复制、编码、统计、字典、Snappy 及原子文件关闭；排除输入构造、结果检查和删除。短场景反复完整写入，保证每个正式样本累计写入至少 1 秒；记录迭代数，以累计时间除以迭代数计算每次耗时。

writer 与不可变 fixture 各使用独立 256 MiB 受管预算。fixture 受管峰值分别为 5.706/91.290 MB，不计入下表 writer 峰值；这不是公共查询整体共用预算的测量。进程 RSS peak 通过 Windows `GetProcessMemoryInfo` 的 `PeakWorkingSetSize` 取得，覆盖 fixture、写入和后续读取。`GetProcessTimes` 的进程 CPU 秒已记录，包含 fixture、所有写入迭代及读取，不能直接当作单次 writer CPU 耗时。RAM 容量和磁盘型号未获取。

## 过滤读取取舍

每次保留的产物都通过生产 footer discovery 和 `RowGroupScanner` 读取 `50000 <= c00 < 50256`，仅投影 c00，逐值检查全部 256 行及执行后受管内存归零。以下计数在全部正式样本中一致，4/64 列也一致。

| 行组 / 页行数 | VFS 返回字节 | Range 请求 | 解码页 / 跳过页 | 跳过行组 |
| ---: | ---: | ---: | ---: | ---: |
| 2048 / 512 | 8,492 | 4 | 2 / 2 | 48 |
| 8192 / 512 | 10,028 | 16 | 2 / 14 | 12 |
| 2048 / 2048 | 8,343 | 2 | 1 / 0 | 48 |
| 8192 / 2048 | 10,647 | 4 | 1 / 3 | 12 |
| 32768 / 2048 | 12,183 | 16 | 1 / 15 | 3 |

这些字节包含数据/页头的 VFS 范围返回量及可能重叠的读取，排除 footer discovery，不是冷磁盘物理 I/O。较大行组会增加本场景中需要遍历的页头，不能只看解码页数量判断读取成本。单次过滤延迟不足正式计时要求，仅作诊断，不发布延迟加速。

另外对 4 列、2,048 行组补查 `identity`：页从 512 增至 2,048 行时，VFS 返回量 **12,558→16,519 字节（+31.5%）**，读取受管峰值 **16,398→49,166 字节**。两次都逐值返回正确的 256 行。该补查只用于确定性 I/O/资源比较，不构成无压缩写入或读取延迟的性能结论。

## 验证与复现

以下检查通过：

```powershell
go test -count=1 ./internal/export
go test ./internal/export -run '^$' -bench '^BenchmarkParquetLayout$' -benchtime=1x -count=1
```

仓库基准的十组产物大小、writer 受管峰值全部与正式测量一致；上述单次基准仅用于执行及指标一致性检查，未混入正式计时样本。

PyArrow 24.0.0 对十份 Snappy 产物逐列比较全部 100,000 行的值、schema、NULL，确认行组数和每组各列 NULL 统计。正式写入各次另检查 metadata、256 行过滤结果及内存归零；没有把最终十份产物的独立校验表述成所有迭代都已外部全量校验。

本轮新增基准与报告，生产行为没有变化，因此未重复全仓库测试、公共 API race 或 DuckDB 差分。没有验证加密、真实远端、多 worker、百万行、冷缓存或 Linux 布局性能。

本机证据位于 `.cache/parquet-layout-2026-11-14/`：`formal-source/main.go`、留存 `layout.exe`、`run.py`、精确命令、环境与 SHA256、原始日志和全部样本、RSS/CPU 指标、`comparisons.json`、独立互读产物及 `interop.json`、普通测试和基准日志。无压缩补查使用独立 `layout-identity.exe`，没有修改留存正式二进制。`record.py` 校验了正式源码/二进制指纹、90 个样本以及两套执行入口的十组大小/峰值一致性。

正式布局对比流程使用上述 `run.py`；仅运行仓库内的单轮原生 writer 比较可用：

```powershell
go test ./internal/export -run '^$' -bench '^BenchmarkParquetLayout$' -benchtime=1s -count=1
```

先将 `TEMP/TMP/GOTMPDIR` 与 `GOCACHE` 指向工作区可写目录。单轮命令不能替代轮换顺序、2 次预热及 7 次正式样本的验收流程。
